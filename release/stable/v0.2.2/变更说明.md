# 变更说明（0.2.2）

## 修了什么

**问题**：在同时装有 FXNT Storage（Create: Storage）的整合包里，JEI 工作台配方页的「+」不会走本模组的缓存供料——对方那个转移处理器与我们在**同一个键**（`(CraftingMenu, minecraft:crafting)`）上注册，而 JEI 的注册表是"最后写入者生效"，它注册得更晚，于是把我们整个顶掉；它的处理器只认"身上背的背包"，因此材料只在缓存里时表现为**灰色「+」＋原版"缺少物品"**。背包里有料时则一切正常（走对方的背包路径）。

## 怎么修的

**不改对方、也不改写 JEI 的表**，只在**客户端**把"谁来回答"接管过来：

- 新增一个 **client-only** 的软失败 mixin（`compat/jei/takeover/TakeoverRecipeTransferManagerMixin`，独立配置 `fmp_jei_takeover.mixins.json`，`required:false`＋`defaultRequire:0`，注入体整段 `catch (Throwable)`）：
  - 挂钩 `mezz.jei.library.recipes.RecipeTransferManager#getRecipeTransferHandler(AbstractContainerMenu, IRecipeCategory)` 的 **RETURN**（JEI 公开 API 方法，也是按钮路径的唯一漏斗）；
  - 判定＝**精确类 `CraftingMenu` ＋ `RecipeTypes.CRAFTING` 引用相等 ＋ 我们的物流面板活着 ＋ 我们持有 3×3 处理器实例**；命中则返回我们自己的处理器（缓存供料），否则**什么都不做**，由原来的处理器（对方的）继续回答；
  - 在 RETURN 取到 **JEI 自己本来会返回的那个处理器**（＝被我们顶掉的那个，小包里就是 FXNT Storage 认得**外装背包**的处理器）并记住它；**我们的处理器先委托它、再用缓存补缺口**（原来这里用的是 JEI 的通用兜底，等于把对方那份能力丢了）。它为空或抛错时回落通用兜底，**永不递归**（插件拒绝把自己存成"被顶掉的那个"）；
  - 决策只在状态变化时各打一行：`FMP JEI takeover: serving …`／`… deferring …`／`displaced handler captured: …`；JEI 升级导致注入失败时**只留一条 WARN**、补丁静默失效，**不会崩游戏**。
- `FmpJeiPlugin` 只多了"保存 3×3 实例 ＋ 访问器 ＋ 记住被顶掉的处理器"，注册逻辑与行为未变。

## 结果看得见（本版新增）

JEI 发起的转移过去是**静默失败**：意图发出即当成功（`FILL_RECIPE` 只回一个 bool），而服务端的裁定只画在**面板的 notice** 上——可 JEI 配方页正盖着面板，**那句话玩家根本看不见**（面板只在它自己的容器界面渲染，被配方页盖住时不渲染；本版核实过渲染门控）。现在：

- **失败**：用 **动作栏**（`player.displayClientMessage(…, true)`，任何界面都可见）说出**我们自己的**原因文案（`gui.create_feed_me_packages.result.*`），并**尽量点名缺什么**——`缺：<物品> ×N, …`（新增 3 个 lang 键，中英同步）；
- **成功**：**不额外刷屏**（材料自己会出现）；面板里的 notice **保持原样**、未改。
- **诚实边界**：那份"缺什么"由**同一个客户端估算**给出（与服务端同源规划器），用于**说明**；但它**只**能作为"能点名 ⇒ 可以灰"的依据，**不能**反过来把"点名不出来"当成拒绝理由；真正的裁决仍归服务端。
- 服务端的失败裁定走同一条动作栏（`LogisticsPanel.fillRecipeForViewer` → 收到 `Snapshot.result` 时说话），**确认超时**也会说一句（不再是沉默）。


## 料源口径（三处都算）

面板在线时，"能不能做"按**三处料源**合起来算：**合成格里现有的 + 玩家背包里的 + 缓存的**；用量顺序是**合成格／背包先用完，缓存补缺口**。

- **点击「+」**：**先委托被我们顶掉的那个处理器**（它可能认得外装背包这类我们看不见的料源；没有它就回落 JEI 的通用转移），按 JEI 自己的规则把合成格与背包里的材料摆上（**服务端裁决语义不变**），再让服务端按剩余缺口从缓存补齐（既有的 `FILL_RECIPE`）。每次点击在日志里留**一行**汇总：谁答的（原处理器类名／通用兜底）、预览与执行结果、缓存补缺结果、以及最终给玩家的那句话。
- **悬停预览（v3，本版最终口径：按钮不许撒谎）**：**能点＝能成；成不了＝灰 ＋ 说清缺什么。** 按顺序，第一条命中即返回：
  1. **原处理器／通用兜底的预览能成** ⇒ **放行**（它的点击路径一定能成：它认随身格＋背着的背包）；
  2. 否则看**我们自己的估算**（与服务端同源规划器：合成格＋随身格＋缓存视图）：
     - **估算 OK** ⇒ **放行**（此路必经服务端 `FILL_RECIPE`，同一口径 ⇒ 点了一定成）；
     - **估算 MISSING 且能点名缺什么** ⇒ **灰**（`USER_FACING`），悬停＝我们的原因文案 **＋** `缺：铁板 ×2`；**有被顶掉的处理器时**再附一句"（仅按缓存与随身格估算，未含外装背包）"，免得玩家以为我们查过他的外装背包；
     - **估算 MISSING 但不能点名**（规划器层面失败）⇒ **放行**（证明不了就不许拒绝——唯一保留的安全阀）；
     - **`NO_SPACE`／`UNSUPPORTED`／`TOO_COMPLEX`** ⇒ **灰**并给对应既有文案（这三条是当场能确证的事实）；
     - **`INACTIVE`** ⇒ 与今天一致（无缓存视图时交回原处理器）。
  - 预览每条链路留**一行 INFO**，字段含 `decision=allow-native|allow-estimate-ok|allow-unprovable|refuse:<reason>` 与 `missing=[…]`，用户下一次日志即可看出按钮为什么亮/灰。
- **对上一轮"始终放行"的更正（不做粉饰）**：上一轮把"面板活着就一律放行"当成修复，其实**判错了**——02:03 的原始日志＋存档 NBT 证明那一刻 `checked=MISSING` **判对了**（该客户端缓存＝云杉原木 64＋铁锭 55，随身铁锭 9，外装背包里是铁块，**全身上下没有铁板**），也就是说我们**拆掉了一个判对的拒绝**，按钮从此开始撒谎。**本次按用户裁定改回"能证明不能做就灰掉并点名缺什么"**；只剩"点击后服务端因竞态仍拒绝"这一种由动作栏兜底说明。
- 材料不足的提示文案已写明三处料源：**"背包、缓存与合成格里的可用材料不足，未转移任何物资"**（en 同步）。

**已知限度**：JEI 自己的转移是"整份摆上或整份不动"，所以"缓存一半、背包一半"这类分摊由"原生命令先做 + 缓存补缺口"两步完成；预览侧按 v3 只拒绝"**能点名**的缺料"与"**当场能确证**的三种事实"，其余一律放行（见 `测试清单.md` B4）。

## 影响面与兼容

- **协议不变**、**存档 schema 不变**（仍 8）、**服务端裁决语义不变**（命中后仍走既有的服务端仲裁与 `unbound`／`panel_not_ready` 文案）。
- **面板不在时（未佩戴坠子／面板未打开）**：**仍走对方**（Create: Storage 的背包供料），与本版之前的行为一致 ⇒ 两个功能都不丢。
- 干净包（没有对方）：占位者本来就是我们，接管是幂等的。

## 已知限度与替代路径

- 若 JEI 客户端界面本身异常（与本模组无关的情况），「+」仍可能不可用；此时**物流面板**与**原版配方书**两条供料路径照旧可用。
- 上一版（0.2.1）发行说明里"与 FXNT Storage 同装时 JEI「+」不可用"这条**已在 0.2.2 修复**。
